## Summary

- **The v1.7 order decision is carried through.** An order completes the moment it is placed and is final. Every statement left from the old lifecycle was removed or rewritten, so that no sentence in the design says an order can be cancelled, has a status, or returns stock.
- **Ticket screens.** One screen per stage (pool, in progress, resolved, archive, cancelled), a status label for each, a list row that shows only the number, type, title, creator, and creation time, and a detail view for the rest. An `OPERATOR` sees the whole pool, but only the in-progress tickets assigned to them, only the resolved tickets they resolved, and no archive.
- **Username and email are fixed.** A user changes neither. Forgot password on the login page is the only recovery. Two empty columns are reserved for a later change flow.
- **Item images.** Accepted types, size, storage, and serving are defined in the usual way for a back-office system.
- **Creators.** The `OPEN` tickets of a disabled creator stay in the pool.
- **Findings left as they are, by the owner's decision.** Deleting or delisting an item cancels the linked tickets of every type, including an order exception, and a person opens a new ticket if the problem remains.

- **Backwards from the page design.** Ticket comments were removed from the first version and their table dropped. The order list index was dropped, because there is no order list. A new section, Screens and Lists, records what the lists read and filter: the home page, paging by two buttons with 10 rows, the stock page and its log by day range, the ticket search for managers and viewers, the user page as a view of what the viewer can manage, the audit log filters, and the account pages (login, sign-up, Forgot password only). The ticket form gained an order number field. The role definitions have no page.
- **Second round of the owner's answers.** (1) Every attempt to place an order, successful or not, gets an order number and is recorded in a new table, `order_attempts`, so the log of a product shows who tried to order what and what came of it. (2) The log of an item is split into a warehouse log (item added or deleted, and stock movements) and a product log (listing history, and the order attempts), each in two parts, and it shows the user who placed an order, not System. (3) The first administrator is created on the server with a console command that asks for the password with hidden input; the forced password change, the flag `users.must_change_password`, and the environment variables for the first administrator are gone. (4) A page holds at most 10 rows.

### The second round: order attempts, the item log, and the first administrator

**Order attempts.** The owner explained that an order attempt gets an order number whether it succeeds or fails, that both are recorded, and that the log of a product should show them. Until now a failed placement left nothing, by design. The new table `order_attempts` is append-only and has one row for each product line of an attempt: the order number, the user, the product, the order (set only when it completed), the quantity, the result (`COMPLETED`, `PRODUCT_DELISTED`, `PRODUCT_CHANGED`, `OUT_OF_STOCK`, `INVALID_QUANTITY`, or `BUSY`), the stock deducted, and the time. The database checks that a completed row has its order and deducted what it ordered, and that a refused row has no order and deducted nothing. A completed row is written in the order transaction, so a success is never missing. A refused row is written in a short transaction of its own after the rollback, holding no lock of the order, so a refusal leaves a record and changes nothing else. The record of a refusal is best effort if the database itself fails. A repeated submission adds no row. `orders` stays the record of successful orders and keeps no status. The ticket of an order exception is always opened by a person, so `source` `SYSTEM` still has no use today, as the owner confirmed.

**The ticket form.** The order number field accepts only the number of a placed order, because a refused attempt changed nothing, so there is nothing to correct. A person reads the number in the result of the order or in the product log of the item. This closes Q-33.

**The item log.** The log button of an item now opens two logs of two parts each. The warehouse log has the item history (`inventory_item_events`: added, deleted) and the stock movements (`inventory_transactions`), with the order number on an order, and with who did it. The product log has the listing history (`product_listing_events`) and the orders (`order_attempts`). For an order the log shows the user who placed it, not System; the owner changed this answer. I put the sales in the warehouse log too, so that every change of the stock quantity is explained there; the owner can remove them. The two logs are two tabs and the parts are sections, which is my layout choice. A deleted item is not on the stock page, so its log can no longer be opened from the screen.

**The first administrator.** The owner asked for the first administrator to be created on the server and not through a page, and was unsure whether to type the password at the console. A console command that starts the application without the web server and asks for the password twice with hidden input is the usual way. It keeps the password out of files, environment variables, and logs, so the forced password change was no longer needed: `users.must_change_password`, T-25, the refusal of a flagged login, and the variables `OPSFLOW_BOOTSTRAP_ADMIN_*` were removed, and T-24 was rewritten. The command can be run again to make another administrator, because whoever can run it controls the server.

**Paging.** A page holds at most 10 rows (the owner changed the maximum from 50), and the page size 10 is also the default.

### The third round: a failed order in a ticket, and the logs by page

**A ticket can name a refused order.** The owner wants an operator to find the number of a failed order in the logs and put it into a ticket. So `tickets.order_id` (a foreign key to `orders`, which a refused attempt does not have) became `tickets.order_no`, the number of an order attempt, placed or refused. It is a plain column and not a foreign key, because the number is shared by the product lines of an attempt and a foreign key to a non-unique key is refused by MySQL 8.4 by default. The service layer checks that the attempt exists when the ticket is created, and `order_attempts` is append-only and never deleted, so the number cannot dangle. `chk_tickets_order_required` now requires an order number for an `ORDER_EXCEPTION` ticket, and the index `idx_tickets_order_status` is on `(order_no, status)`. The ticket form's `ORDER_NOT_FOUND` now means that no attempt has the number.

**Logs by page.** The owner redefined the logs: the product page has the product log, and the stock page has the warehouse log. Each has two kinds of record, listing records and order records on the product page, item records and stock movements on the stock page, and each is read in three ways: all records of one kind (View records, choose one of two), one chosen product or item (a picker), and the own log of one (a View button on its row). This replaces the earlier layout of two tabs on the stock row. The order records list every attempt with its number, so the number of a refused order is found there. Four time indexes were added (`idx_product_events_created`, `idx_order_attempts_created`, `idx_item_events_created`, `idx_inventory_tx_created`) for the logs of all products and all items, which until now were indexed only by product or item. A delisted product and a deleted item are no longer rows on their pages, so their records are reached through the first two ways.

**The searchable picker** is a shared control for choosing a product or an item by name: a scrolling dropdown sorted alphabetically, with a text box that narrows it. It offers every product ever listed and every item ever added (deleted ones marked, with the SKU shown), and the ticket form and the filters reuse it.

### Orders: statements removed or rewritten

- The diagram note no longer says an order is cancelled and its stock returned.
- The `orders` table responsibility no longer lists a status or the details of a cancellation.
- The deleted-item rule no longer says that an order placed before the deletion can still be cancelled.
- The log format of `ITEM_DELETED` no longer has `writtenOff`, because a deletion does not touch the stock.
- The field list no longer has `orders.cancel_reason`, which the table does not have.
- The permission defaults no longer say that an operator may cancel an order. The sentence about cancelling tickets was also corrected to the matrix: an `OPERATOR` cancels only their own tickets.
- "The status gate" now refers only to ticket transitions. The retry rule, the concurrency table, and the constraint list no longer mention an order status or order cancellations.
- The description of the verification run no longer mentions a cancellation or `RETURN` as part of the model.
- A stray character after the `user_roles` key was removed, and the soft-deletion paragraph now names `users` and `inventory`, not `products`.
- Correcting a wrong order says what happens when the item was deleted: the stock of a deleted item no longer matters, so there is nothing to put back, and the ticket is opened without a link and names the order.

### Ticket screens and who sees what

- Five screens, each with a status label: Pool (waiting to be taken), In progress, Resolved, Archive (archived), and Cancelled.
- `ADMIN`, `MANAGER`, and `VIEWER` see every ticket on every screen. An `OPERATOR` sees the pool in full, the in-progress tickets assigned to them, the resolved tickets they resolved, and the cancelled tickets they created or last held. An `OPERATOR` has no archive screen.
- A list row shows the ticket number, the type, the title, the creator, the creation time, and the status label. The description, order, linked items, follow-up links, comments, assignment history, resolution, and cancel reason are in the detail view only.
- The service layer filters by user id for an `OPERATOR`. The frontend alone does not decide it.
- Consequences the owner accepted: an operator's own `OPEN` ticket leaves their lists when someone else takes it, and a ticket an operator resolved leaves their Resolved screen when it is archived. The follow-up field still finds any ticket number.
- The archive screen text and the cancelled-area text were changed to match, and the Permission Matrix has two rows for viewing tickets.

### Accounts

- Username and email cannot be changed. `users.username_changed_at` and `users.email_changed_at` (both `DATETIME(3)`, empty) are reserved for a later flow. The unique keys stay, so a value is never reused.
- The `OPEN` tickets of a creator who is disabled or soft-deleted stay in the pool.

### Item images

- JPEG, PNG, or WebP, at most 2 MB, with the type checked from the file content. The application stores the file under a random name in a configured folder outside the web root, and `inventory.image_url` holds the relative path. Replaced images and the images of deleted items are kept and cleaned up by a later job.
- The size limit and the types are in Operating Parameters.

## Decisions Made In This Iteration

| Decision | Choice | Alternative considered |
| --- | --- | --- |
| Manual stock changes on a deleted item | Still refused. The stock of a deleted item no longer matters, so a wrong order of a deleted item needs no stock correction | Allowing changes on a deleted item, which would keep a row alive that every other rule treats as gone. The owner may revisit this (Q-30) |
| Tickets of a deleted or delisted item | Cancelled for every type. A person opens a new ticket if the problem remains | Sparing `ORDER_EXCEPTION` tickets, which the owner declined |
| Who opens an order-exception ticket | Always a person. The program opens no ticket | Tickets opened by the system for failed attempts, which the owner did not want |
| What an operator sees | Pool in full, own in-progress, own resolved, own cancelled, no archive | The same screens for every role |
| Rows of a ticket list | Number, type, title, creator, creation time, status label | Showing the description in the list |
| Cancelled area for an operator | Only the tickets they created or last held (confirmed by the owner) | No cancelled area for an operator |
| Username and email | Fixed after sign-up, with two reserved columns | Columns for a change flow now, or a history table |
| Image storage | A random file name in a folder outside the web root, a relative path in the database | Storing the image in the database, or keeping the name the person gave |
| Tickets of a disabled creator | Stay `OPEN` | Cancelling them, or returning them to the creator |
| Recording a failed order attempt | A new append-only table `order_attempts`, with one row for each product line. A completed row is written in the order transaction, a refused row in a short transaction after the rollback | Putting the attempts in `operation_logs` (JSON, no constraints on the outcome); giving `orders` a result column, which would make an order a status-carrying record again |
| Order number of a refused attempt | Generated for every attempt and shown in every result. A ticket can name only the number of a placed order | Numbers only for placed orders; or a ticket that names a refused attempt, which would need a second foreign key |
| Who is shown for a sale in the log | The user who placed the order (the owner's second answer) | The word System (the first answer) |
| Where sales appear | In the warehouse log as stock movements, with the order number, and in the product log as order records | Only in the product log, which would leave unexplained gaps in the stock history |
| Layout of the item log | Replaced in the third round by the logs by page | One mixed list, which would need a union of two tables for paging |
| What a ticket names for an order | The number of any order attempt, a refused one included, in a plain column checked by the service layer | The id of a placed order (a foreign key), which cannot name a refused attempt; a foreign key to the non-unique order number, which MySQL 8.4 refuses by default; a header table for attempts, which adds a table |
| Layout of the logs | By page: the product log on the product page and the warehouse log on the stock page, each read as all records, one chosen, or the own log of one | Two tabs on the stock row (the earlier layout) |
| First administrator | A console command on the server with a hidden password prompt; no flag, no environment variable | Environment variables and a forced password change, which needed a page or a console step |
| Page size | 10, and also the most | 10 by default and 50 at most |

# 06 订单创建核心流程

## 今天要建立的理解

订单创建是整个项目最重要的后端逻辑。它不是简单 insert 一条订单，而是一组必须保持一致的业务动作：校验商品、校验库存、扣减库存、创建订单、创建订单明细、记录日志。

## 你要重点考虑的问题

先考虑成功流程。一笔订单创建成功，应该同时满足：订单存在，订单明细存在，库存减少，日志记录存在。任何一个环节失败，都不能留下半成功状态。

再考虑失败流程。商品不存在怎么办？商品已下架怎么办？库存不足怎么办？数据库写入失败怎么办？你要把这些错误当成正常业务情况来设计，而不是等报错再说。

最关键的是事务。库存扣减和订单创建必须在同一个事务里，避免出现“订单创建了但库存没扣”或“库存扣了但订单没创建”的情况。

还要考虑并发。两个用户同时买同一个低库存商品时，代码里先查库存再扣库存可能不够安全。你要了解数据库锁、乐观锁、悲观锁、条件更新这些概念。

## 建议你查什么

推荐关键词：

- Spring transaction order inventory consistency
- inventory deduction concurrent orders
- optimistic lock inventory version
- pessimistic lock select for update
- order status machine design

不要急着全实现，先理解几种方案的取舍。初级项目可以选一种相对清晰的方案，比如用事务加条件更新库存。

## 怎么问 AI 更有效

可以问：

“我现在的订单创建流程是先查库存，再扣库存，再创建订单。请你从并发和事务角度检查会不会有问题，并给我适合 Spring Boot 初级项目的改进方案。”

也可以问：

“请你帮我设计订单状态机，说明 CREATED、PAID、CANCELLED、FAILED 之间哪些状态流转是允许的，哪些不应该允许。”

## 你应该产出的东西

你需要完成创建订单接口，并能验证：

- 正常创建订单
- 库存不足创建失败
- 下架商品创建失败
- 失败时库存不被错误扣减
- 成功时订单、明细、库存、日志一致

你还应该写一段说明：订单创建为什么需要事务。

## 复盘问题

- 什么叫数据一致性？
- 为什么订单和库存要放在同一个事务里？
- 并发下库存可能出现什么问题？
- 如果面试官问我库存超卖怎么解决，我能不能讲清楚？
